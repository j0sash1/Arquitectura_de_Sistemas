# Shortly Microservices Architecture

## 1. Introduction

Shortly is a URL shortening platform that allows users to create, manage, and 
access shortened URLs. The original application is implemented as a monolithic
ASP.NET Core system containing user management, URL management, redirection,
and statistics functionalities within a single deployable unit.

To improve scalability, maintainability, and fault isolation, the system has been
redesigned as a microservices-based architecture following the C4 model. The
proposed architecture separates responsibilities into independent services that can
be developed, deployed, and scaled independently.

---

## 2. Service Decomposition Rationale

The monolithic architecture was decomposed according to business capabilities and the Single Responsibility Principle.

### API Gateway

The API Gateway acts as the single entry point for all client requests. It is responsible for routing requests to the appropriate microservice and hiding internal service topology from clients.

**Responsibilities**

- Request routing
- Centralized entry point
- Security and future rate limiting

**Boundary**

- Does not contain business logic
- Delegates processing to backend services

--- 

### URL Service

The URL Service manages the lifecycle of shortened URLs.

**Responsibilities**

- Create short URLs
- Retrieve URL information
- Delete URLs
- Manage URL metadata

**Boundary**

- Owns all URL-related business logic
- Does not manage authentication or statistics

### Redirect Service

The Redirect Service resolves shortened URLs and redirects users to the target destination.

**Responsibilities**

- Resolve short URLs
- Redirect requests
- Publish click events

**Boundary**

- Focused exclusively on high-performance redirection
- Does not calculate statistics

The service is separated because URL redirection is expected to receive the highest traffic volume in the system.

---

### Identity Service

The Identity Service manages authentication and user information.

**Responsibilities**

- User registration
- User authentication
- Password management
- Authorization support

**Boundary**

- Owns user accounts and credentials
- Does not manage URLs

### Stats Service

The Stats Service processes analytics and usage information.

**Responsibilities**

- Collect click statistics
- Generate metrics
- Provide reporting information

**Boundary**

- Consumes events generated by other services
- Does not participate in user-facing operations

## 3. Communication Patterns 

The architecture combines synchronous and asynchronous communication patterns.

**Synchronous Communication**

REST APIs over HTTPS are used when an immediate response is required.

Examples:
    - Client → API Gateway
    - API Gateway → URL Service
    - API Gateway → Identity Service
    - API Gateway → Redirect Service

Protocol:
    - HTTP/REST
    - JSON payloads

This approach is suitable for request-response interactions such as creating URLs, authenticating users, and retrieving information.

---

### Asynchronous Communication

RabbitMQ is used for event-driven communication.

Example flow:

    1. Redirect Service processes a redirect.
    2. Redirect Service publishes a ClickRegistered event.
    3. RabbitMQ distributes the event.
    4. Stats Service consumes the event.
    5. Statistics are updated.

Benefits:
    - Loose coupling
    - Better scalability
    - Improved fault tolerance
    - Reduced latency in redirection requests

---

## 4. Data Ownership

Each microservice owns its own data and is responsible for managing its persistence. This approach avoids direct database sharing between services, reduces coupling, and allows each service to evolve independently.

### URL Service

**Owns:**

- URL records
- Short URL identifiers
- URL metadata

The URL Service is the only service allowed to create, update, or delete shortened URLs.

---

### Identity Service

**Owns:**

- User accounts
- Credentials
- Authentication information

No other service accesses or modifies user data directly. User-related information is obtained through service communication when necessary.

---

### Stats Service

**Owns:**

- Click counts
- Usage statistics
- Aggregated analytics

Statistics are maintained independently from URL management to improve scalability and allow analytical workloads without affecting user-facing operations.

---

### Data Consistency

The architecture combines synchronous and asynchronous communication depending on the type of data being exchanged.

- Critical operations, such as URL creation and authentication, use synchronous REST communication to ensure immediate consistency.
- Click statistics are updated asynchronously through RabbitMQ events. After a successful redirect, the Redirect Service publishes a `ClickRegistered` event, which is consumed by the Stats Service.

This event-driven approach provides eventual consistency for analytics while keeping the redirection process fast and minimizing coupling between services.

---

## 5. Scalability Considerations

One of the primary motivations for adopting microservices is independent scalability.

**Redirect Service**

Expected to scale the most.

Reasons:
    - Every URL access generates a redirect request.
    - High read traffic.
    - Benefits from Redis caching.

Multiple instances can be deployed behind a load balancer.

**Stats Service**

Can scale independently when click volume increases.
Additional consumers can be added to process RabbitMQ events.

---

**URL Service**

Moderate scaling requirements.
Traffic is significantly lower than Redirect Service because URL creation occurs less frequently than URL access.

---

**Identity Service**

Generally requires lower scaling levels because authentication requests are less frequent than redirect requests.

---

## 6. Failure Modes and Resiliency

**URL Service Failure**

Impact:
    - Users cannot create or manage URLs.

Mitigation:
    - Health checks
    - Automatic restart policies
    - Multiple service instances

---

**Redirect Service Failure**

Impact:
    - Short URLs stop redirecting.

Mitigation:
    - Load balancing
    - Multiple replicas
    - Redis cache for fast recovery

---

**Identity Service Failure**

Impact:
    - Users cannot authenticate.

Mitigation:
    - Service replication
    - Database backups
    - Token-based authentication to reduce dependency on repeated logins

**RabbitMQ Failure**

Impact:
    - Statistics updates are delayed.

Mitigation:
    - Message persistence
    - Retry mechanisms
    - Dead Letter Queues

**Stats Service Failure**

Impact:
    - Analytics become temporarily unavailable.

Mitigation:
    - Event buffering in RabbitMQ
    - Service restart without data loss

## Conclusion

The proposed architecture decomposes Shortly into independent microservices aligned with business capabilities. This design improves scalability, maintainability, fault isolation, and future extensibility while preserving the core functionality of the original monolithic application.
